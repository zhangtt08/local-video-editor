# ADR-001：本地服务作为唯一剪辑状态入口

状态：采纳。日期：2026-10-03。

## 问题

外部 Agent、MCP 客户端和未来桌面界面需要操作同一项目，且不能各自实现不同的剪辑规则。
当前需要其他 Agent 可接续开发的稳定底座；还没有媒体引擎或现有代码约束。

## 比较

| 方案 | 数据/控制流 | 优点 | 成本与风险 | 撤回成本 |
|---|---|---|---|---|
| Python 模块化本地服务（选用） | MCP/桌面 → HTTP → 时间线规则 + SQLite | 路径统一，媒体生态易接，真实协议可验收 | 桌面打包需附带 Python；一个 SQLite writer | 低：传输和媒体可替换；项目 schema 需迁移 |
| GUI 内置全部状态与自动化 | Agent → 桌面进程 → GUI 状态 | 直连现有 GUI 播放功能 | 当前无 GUI；headless 运行与重试语义耦合 UI | 中到高 |
| 多个独立微服务 | API → 项目/素材/渲染服务 | 单独扩展和故障隔离 | 当前不需要部署与分布式一致性复杂度 | 高 |

三个方案都能设计向内依赖，但只有第一方案现在用最少运行组件满足统一执行路径。
当前没有跨机器多服务生产流量，因此不应用微服务上线就绪标签。时间线算法在选中方案中是精确的分轨排序检查，而非近似。

## 决定

- 用户已选择 Python 核心，桌面后续独立接入。
- HTTP 服务是项目状态的唯一写入口；MCP 是官方 SDK stdio 到 HTTP 的薄适配器。
- 剪辑命令与项目 JSON 契约统一；Pydantic 为共享 schema 工具，不复制 dataclass 镜像。
- 时间线规则为纯 reducer；SQLite 持久化门面同时负责事务、版本与回执。
- 精确 tick 采用 70,560,000/秒，支持当前声明的帧率和 44.1/48/96 kHz 采样率。
- 渲染后续读取固定 revision 的不可变快照，先按 worker 进程隔离，不引入外置队列。
- 新功能通过具体契约、命令和计划节点演进。当前没有通用插件系统。

API/MCP 两种真实传输使 adapter 边界成立；没有第二个数据库实现，不增加抽象 repository。
分发命令采用明确的判别联合与小型 reducer；不创建每条命令一个类的执行框架。

## 代价与重新评估信号

全量快照与回执增长、Python 桌面打包体积、复杂效果的性能都需要后续实际测量。
若本地写锁等待持续影响交互，再评估存储；若需要多个远程用户协作，再设计权限与服务部署；若媒体 worker 资源争用，再增加调度。
初个真实视频闭环应是“受信导入 → 切分/拼接 → 固定 revision 导出”，完成后再测性能与质量。

## 验证与回退

真实 HTTP + 官方 MCP stdio 自检覆盖统一命令、失败回滚、并发版本竞争、重复请求与历史恢复。
桌面壳和媒体后端尚未选定，不影响此接口。更换存储保留 /v1 契约，数据库升级前备份；不能通过删除历史/回执进行所谓回退。
